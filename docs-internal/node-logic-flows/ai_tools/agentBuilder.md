# Agent Builder (`agentBuilder`)

| Field | Value |
|------|-------|
| **Category** | ai_tools (dedicated AI tool, group `("tool", "ai")`) |
| **Backend handler** | `BaseNode.execute()` dispatches each operation to a method on [`AgentBuilderNode`](../../../server/nodes/tool/agent_builder/__init__.py). |
| **Tests** | [`test_agent_builder.py`](../../../server/tests/nodes/test_agent_builder.py) (editor-built workflows), [`test_agent_builder_employee.py`](../../../server/tests/nodes/test_agent_builder_employee.py) (hired employees), [`test_agent_builder_atomic_ops.py`](../../../server/tests/nodes/test_agent_builder_atomic_ops.py) (ledger, retries), [`test_rebind_filters.py`](../../../server/tests/services/test_rebind_filters.py) |
| **Skill (if any)** | [`server/skills/assistant/agent-builder-skill/SKILL.md`](../../../server/skills/assistant/agent-builder-skill/SKILL.md) |
| **Dual-purpose tool** | tool-only — `ToolNode` exposed to the LLM as `agent_builder` (`tool_name` class attr) |

## Purpose

Lets the calling agent inspect the workflow and add tools or skills. A managed
Chat Employee can add specialists under a selected manager. An editor team lead can
also add its own specialists. One node, one
`Params` model with an `operation: Literal[...]` discriminator, multiple
`@Operation` methods; the LLM sees one tool with a select-style `operation`
field.

Read-only `inspect_node`, `search_docs`, and `read_doc` operations expose
current plugin contracts and a manifest of shipped project Markdown.
Inspection includes live parameter/output schemas, handles, credential IDs,
locked fields, availability and related documents, without stored secrets.
Search is capped at 50 results; reads at 24000 characters with continuation
offsets. Relative document links resolve within the manifest; arbitrary paths
cannot be read. Archived documents are marked and ranked after current docs.
Live schemas take precedence over conflicting prose. The distribution bundle
is generated by `server/services/builder_documentation.py` into
`server/resources/builder_documentation.json`.

Tool/member reuse is checked again inside the graph mutation transaction.
Concurrent requests cannot bind duplicate same-type callable identities;
intentional custom `aiAgent` teammates remain repeatable. Added specialists
inherit their manager's model and receive purpose, private Context, validated scoped
tools and selected skills. On a managed hire, that manager's Task Manager
exposes a bound `spawn_<teammate>` for each connected specialist. The manager
supplies instructions and optional task dependencies, then reviews the result.

A new Coding Agent also receives its connected Pi tool nodes through the same
[`coding_agent_additions`](../../../server/services/coding_agent_recipe.py)
recipe used by the editor/API and Hire: Read File, Write File, Edit File, Bash,
Search Text, Find Files and List Directory, plus PowerShell on Windows.
An explicitly configured Pi tool uses the same default node. On a managed
team, repeating `add_subagent` for the Coding Agent returns its existing
`member_id`. Supplying `tool_types` or `skill_names` equips that member with
the requested capabilities. See [Coding Agent](../specialized_agents/coding_agent.md).

Every change is saved through
[`services/workflow_storage/mutate.py`](../../../server/services/workflow_storage/mutate.py)
`apply_graph_additions`, the server's one path for growing a saved workflow
(Turn on Talk uses it too): one transaction, canonical ids, labels unique
against the graph, the edge handles of
[`services/graph_build.py`](../../../server/services/graph_build.py), real
`NodeParameter` rows, and a `workflow_ops_apply` push with `persisted: true`
so an open editor adopts the change without saving it.

On a hired employee (the workflow has an employee row) it applies the rule
Hire applies, [`services/employees/policy.py`](../../../server/services/employees/policy.py),
which is how an employee extends itself from Talk.

| Handle | Connection type | Required | Purpose |

## Parameters

The model supplies `AgentBuilderParams` as tool arguments. The
`displayOptions.show` column gives the editor's field visibility. The
description gives the operations that read the field.

| Name | Type | Default | Required | displayOptions.show | Description |
|------|------|---------|----------|---------------------|-------------|
| `operation` | enum | `inspect_canvas` | no | - | `inspect_canvas`, `inspect_node`, `search_docs`, `read_doc`, `plan_update`, `apply_update`, `add_tool`, `add_skill`, `add_subagent`, `create_workflow` |
| `node_type` | string | `""` | no | `operation == add_tool` | Tool type from `available_tools` for `add_tool`, or plugin type for `inspect_node` |
| `node_id` | string | `""` | no | - | Saved node to inspect with `inspect_node` |
| `query`, `limit` | string, integer | `""`, `12` | no | - | Search terms and result limit (1–50) for `search_docs` |
| `document_id`, `offset`, `max_chars` | string, integer, integer | `""`, `0`, `12000` | no | - | Manifest ID, starting character and character limit (1–24000) for `read_doc` |
| `app_id` | string | `""` | no | `operation == add_tool` | The tool's app, when its `available_tools` entry names one: required for a type several apps share (each custom connector is its own app) |
| `target_member_id` | string | `""` | no | - | Member receiving a tool or skill (defaults to caller), or the manager receiving a new direct report (defaults to the Orchestrator in v3). |
| `skill_name` | string | `""` | no | `operation == add_skill` | Skill name (SKILL.md frontmatter `name`, or a library skill's name), from `available_skills` |
| `agent_type` | string | `""` | no | `operation == add_subagent` | Type of specialist to add under the selected manager. |
| `purpose` | string | `""` | no | - | Responsibility and acceptance criteria for a new specialist |
| `tool_types`, `skill_names` | string arrays | `[]` each | no | - | Tools and skills to assign with `add_subagent`, up to 20 entries per list |
| `tool_parameters` | object | `{}` | no | - | Settings keyed by tool type. For `add_tool` the key is `node_type`. For `add_subagent` each key must appear in `tool_types`. Builder validates settings against the plugin contract. |
| `change_operation` | enum | `apply_saved` | no | - | Change for `plan_update` or `apply_update`. Accepts `add_tool`, `add_skill`, `add_subagent` or `apply_saved`. |
| `dry_run` | boolean | `false` | no | - | Preview a tool, skill or specialist addition before saving the graph |
| `stop_work` | boolean | `false` | no | - | Interrupt current work during `apply_saved` when the owner explicitly requests it |
| `workflow_name` | string | `""` | no | `operation == create_workflow` | Employee display name for the shared Hire pipeline |
| `workflow_description` | string | `""` | no | `operation == create_workflow` | Optional one-line description |

### Output payload (TypeScript shape)

```ts
{
  operation?: string;
  // One plain sentence on an employee refusal: the agent passes it on.
  summary?: string;
  member_id?: string;            // add_subagent: node ID of the specialist
  request_id?: string;
  required_access?: Array<{ request_id: string; app: string; action: string; member_id: string }>;
  validation_issues?: Array<Record<string, unknown>>;
  activation_state?: string;     // planned, blocked or saved for staffing changes
  saved_revision?: string;
  binding_results?: Array<{ node_id: string; saved: boolean; available_in_run: boolean }>;
  // add_tool / add_subagent: saved ops scoped to the caller's bindings,
  // plus a saved tool the caller's run lacks. Specialist-owned tool nodes
  // are announced to editors but excluded from the caller's tool rebind.
  // Empty for add_skill.
  operations?: Array<Record<string, unknown>>;
  // inspect_canvas extras:
  nodes?: Array<{ id; type; label; key_params }>;
  edges?: Array<{ source; target; source_handle; target_handle }>;
  you?: { node_id: string; incoming: unknown[]; outgoing: unknown[] } | null;
  employee?: { asks_first: boolean; agents: string[] };   // hired employees only
  available_tools?: Array<{ type; display_name; description; app?; app_id?; connected?; read_only? }>;
  available_agents?: Array<{ type; display_name; description }>;
  available_skills?: Array<{ name; description }>;
  // create_workflow extras:
  workflow_id?: string;
}
```

## Logic Flow

```mermaid
flowchart TD
  A[BaseNode.execute -> operation method] --> C[caller = ctx.raw invoking_agent_node_id or parent_node_id<br/>canvas = saved workflow.data<br/>employee = employee row for the workflow]
  C --> R{operation}
  R -- inspect_canvas --> I[canvas + key params from rows<br/>catalogues: registry for an editor-built workflow,<br/>policy-allowed tools + library and Discover skills for an employee]
  R -- add_tool --> T{allowed?<br/>registry catalogue / policy.check_tool}
  T -- no --> Tn[summary = reason, operations = empty]
  T -- yes --> Tp[target: caller or selected employee member<br/>reuse private binding or create separate instance<br/>split legacy shared binding for this target]
  Tp --> S[apply_graph_additions<br/>ledger key = tool call id scoped to the run]
  S --> Tb{saved tool missing from this run?}
  Tb -- yes --> Tbo[prepend a bind-only add_node]
  R -- add_skill --> K{found? library first, then offered built-ins<br/>employee: policy.check_skill, Discover only}
  K -- no --> Kn[summary = reason]
  K -- yes --> Kp[merge into each target's Skills node row<br/>wire the shared one to a target without one, else a new Skills node]
  Kp --> S
  R -- add_subagent --> G{managed Talk or team lead,<br/>permitted specialist type}
  G -- no --> Gn[summary = reason]
  G -- yes --> Gp[agent + private Context + scoped tools<br/>Coding Agent includes Pi defaults<br/>output-top -> input-teammates]
  Gp --> S
  R -- create_workflow --> W[trusted owner request -> shared Hire pipeline -> configured employee team]
```

## Decision Logic

- **Caller**: `ctx.raw["invoking_agent_node_id"]` (Temporal) or
  `ctx.raw["parent_node_id"]` (every path), never guessed from edges: one
  Agent Builder node can serve several agents. In an editor-built workflow
  the caller is the target, so with none nothing is added ("Only an agent can
  ask me to add things."); an employee's tool target is `target_member_id`
  or the caller, validated against its `node_roles` for both legacy and team
  employees. Membership is checked again during the mutation transaction.
- **Saved graph**: operations read `workflow.data` fresh, so calls in one run
  see each other. A workflow that is not saved, or whose caller is not in the
  saved graph yet, gets "Save the workflow first".
- **Ledger**: the mutation id is `agent-builder:<execution_id>:<tool_call_id>`
  (the request's hash when the runtime passes no call id). Every mutating call
  goes through `apply_graph_additions`, even with nothing to add, so a retried
  call replays the first attempt's result (and announces it again) instead of
  adding twice.
- **Editor-built workflow**: tools from `_allowed_tool_types()` (ToolNodes and
  `usable_as_tool` plugins, no chat models, minus `agentBuilder` /
  `masterSkill` / `taskManager` and the allowlist's `disabled_nodes` /
  `disabled_groups`); skills from the SkillLoader registry outside
  `disabled_skill_folders`, plus the owner's library. The target is the
  caller.
- **Hired employee**: each tool belongs to one selected member. `check_tool`
  checks the hire allowlist and the connection for the selected app. With
  Ask first on, a tool with a runtime approval policy can hold a send, refuse
  a payment or restrict the browser to reading. For a tool that can send or
  spend and has no runtime policy, Builder uses the app's `ask_first_params`
  when available and otherwise declines the addition. The Clock gets the
  owner's `profile_timezone`. A type
  whose app a parameter names (`app_field`: the Custom Connector) is listed
  once per app with its `app_id`, needs it in `add_tool`, and counts as the
  target's tool only on a node naming the same app.
  `check_skill` refuses `skill` and `*-personality`; skills come from the
  library (all of it, on or off for new hires) and the Discover folder
  (`server/skills/employee/`), text copied in. Managed Chat routes
  `add_subagent` to the selected manager. An authenticated owner can request
  a specialist directly when Ask first is off. When the configured rule
  requires review, Builder returns `required_access` and the employee
  page offers **Allow and add**. This saves the reviewed change. Talk can
  activate it with `apply_update` using `change_operation: "apply_saved"`,
  or the owner can select **Apply**. Once active, the lead can assign work
  to the specialist through its Task Manager.
- **One concrete tool owner**: a same-type tool on another member is never
  attached to this target. The target reuses its private node or receives a
  fresh node. Ownership and parameter rows are read inside the mutation
  transaction. A legacy shared binding is replaced only for this target with
  a separate configured instance; the old node, settings and other targets'
  edges remain intact. Different agents may have independent same-type nodes.
  An active snapshot retaining the shared callable receives no new binding
  during repair, avoiding duplicate names; the result reports saved access
  with `available_in_run: false` until Apply or a clean run.
- **Bind-only**: a deployed run starts from the generation's frozen snapshot.
  A tool saved earlier (an earlier message) but missing from this run's canvas
  comes back as an `add_node` op with the saved id and row, and nothing is
  saved or announced, so the agent can call it now instead of hearing
  "already wired".
- **Skills**: each target's Skills node gets the entry; a target without one
  is wired to the shared node (never a second: two on one agent collide on
  the Skill tool's own entry), else a new Skills node (`Skills` for an
  employee, `Master Skill` otherwise). An enabled skill changes nothing. A
  built-in keeps no text in an editor-built workflow (edits to its SKILL.md
  apply); a library skill always carries its text (the runtime's fallback
  reads files only).
- **When it works**: a tool is bound for the rest of the calling agent's run
  (`auto_rebind_tools`, on by default; summary "Available immediately" / "You
  can use it now", else "Available on your next turn"). A skill merged into an
  existing Skills node applies from the next message. On a managed team,
  **Apply** activates new graph connections for future assignments.
- **`add_subagent`** connects a new specialist to the selected manager.
  Managed Talk can make the call from the authenticated owner conversation.
  Registered specialist types have one teammate each. Custom `aiAgent` types can repeat.
  The new agent gets its own Context (`context_of`) and an `output-top` →
  `input-teammates` edge. Coding Agent's Pi defaults are separate saved nodes
  connected only to that specialist. Creation is refused if a required default
  is disabled. The employee grant request includes default and explicit tool
  types; mutation authorization and child grants cover the resulting nodes.
  The optional [Write Todos](./writeTodos.md) tool is not a Pi default.
- **`create_workflow`** calls the shared owner-verified Hire pipeline when
  `_CREATE_WORKFLOW_ENABLED` is enabled. The v3 recipe saves the reviewed
  reporting lines with an `ai_employee` Chat Employee and its permanent
  `orchestrator_agent` direct report. Chat uses its Task Manager to submit
  work and check status. Agent Builder excludes `taskManager` from
  `add_tool`, so callers obtain these connections through Hire.
- **Authority**: employee changes require reusable owner grants scoped to the
  target member and complete configuration. Grant scope and revocation are
  rechecked inside the graph mutation transaction. Public app messages cannot
  authorize expansion. `plan_update` validates without a graph mutation;
  `apply_update` repeats validation and authority before saving, or safely
  activates saved capabilities after admitted work finishes.

## Side Effects

- **Database writes**: `apply_graph_additions` — `workflow.data` gains nodes
  and edges, new nodes get fresh `NodeParameter` rows, Skills rows are merged,
  and a `RuntimeMutation` ledger row is written, all in one transaction.
- **Broadcasts**: `workflow_ops_apply` with `persisted: true`
  (`services.workflow_ops.broadcast_workflow_ops`), then the graph-changed
  listeners (`notify_graph_changed`: Home's employee summary, with its
  pending-changes notice). A bind-only result announces nothing.
- **External API calls**: none. Connection state is read for employees
  (`services.employees.connections`).
- **File I/O**: reads SKILL.md files through the SkillLoader.

## Edge cases & known limits

- A running employee uses its admitted team until Safe Apply activates the
  saved graph. Talk can immediately use its own newly bound tools when
  rebind is enabled. A skill merged into an existing Skills node applies
  from the next message.
- Both native and Temporal paths deduplicate existing node IDs before tool
  name checks. Specialist-scoped tools are excluded from the caller's rebind.
- Managed team members, tools, skills and Context roles are refreshed in the
  same transaction as graph additions. Results distinguish saved revision,
  current-run bindings and deployment activation.
- A Dev canvas Run with unsaved edits cannot be changed ("Save the workflow
  first").
